# CVEs

Every vulnerability matched against the [SBOM](https://en.wikipedia.org/wiki/Software_supply_chain) of the MS Windows builds,
since 2026-10-22 for the stable builds (the beta and LTS builds will be added later).

The [SBOM vulnerabilities workflow](../../.github/workflows/sbom.yml) scans the latest builds every day,
using the CPE and PURL references maintained by MSYS2 ([`msys2_sbom.py`](../../packaging/MSWindows/msys2_sbom.py)),
and fails when it finds a vulnerability which is not recorded below,
unless it only affects one of the [ignored packages](#ignored-packages).
Packages without any CPE or PURL reference cannot be matched, so their vulnerabilities are not tracked by these scans ([#5097](https://github.com/Xpra-org/xpra/issues/5097)).

| Column | |
|---|---|
| `CVE` | the vulnerability, in numerical order |
| `Package` | the packages it was matched against |
| `Severity` | as reported by the scanner |
| `Issue` | short description |
| `Upstream fix` | the first upstream version that fixes it, when known |
| `Live` | `🔴 on` if it applies to our builds, `off` if it does not (false positive, code we do not use, etc - say why in `Notes`): the scans no longer report it |
| `First xpra version` | the xpra version(s) where it was first found |
| `Fixed in xpra` | the first xpra version(s) with the fix |
| `Ticket` | link to the issue tracking it, if needed |
| `Notes` | analysis |

## Ignored packages

Some libraries are only bundled because another library we need links against them,
but the code paths that would use them are never reached.
The scans ignore every vulnerability found in these packages.

| Package | Reason |
|---|---|
| `libssh2` | only used by `curl` for `scp://` and `sftp://` URLs, which nothing gives it: xpra's own ssh connections use `paramiko` or the bundled OpenSSH |
| `p11-kit` | `gnutls` links against it, but its PKCS#11 modules are not bundled (`BUILD.py` deletes `lib/p11-kit*`), so there is nothing to load or talk to |

## Image data

Image data received from the peer is only handed to Pillow once
[`open_only`](../../xpra/codecs/pillow/decoder.py) has recognized its header as one of the formats allowed in that context:
* `png`, `jpeg` and `webp` for window pixels, cursors, icons and webcam frames
* the same plus `bmp`, `ico`, `ppm` and `xpm` for clipboard images on MS Windows (`XPRA_CLIPBOARD_IMAGE_FORMATS`)

Animated PNG data, including PNG frames embedded in an ICO file, is detected as `apng`, which no context allows ([#5096](https://github.com/Xpra-org/xpra/issues/5096)).
`BUILD.py` also deletes most Pillow plugins, and `xpra.codecs.loader` blocks many more, including `TiffImagePlugin`.

Xpra only processes the first image frame: it never seeks between frames or uses `ImageSequence.Iterator`.
The PSD, MPO, DCX and MIC loaders affected by CVE-2026-96639 are both removed from the MS Windows builds and blocked at import time.
An MPO file can start with a JPEG header, but Pillow cannot switch to the MPO loader when that plugin is absent.

BMP decoding is reachable through the MS Windows clipboard:
[`set_clipboard_image()`](../../xpra/platform/win32/ctypes_clipboard.py) allows BMP by default,
then `image_to_bitmap()` converts the image to RGBA, loading its pixels, including RLE-compressed BMP data.
JPEG decoding also parses EXIF implicitly:
Pillow's [`_read_dpi_from_exif()`](https://github.com/python-pillow/Pillow/blob/12.3.0/src/PIL/JpegImagePlugin.py)
calls `getexif()` during `Image.open()` when EXIF is present and DPI is missing.
JPEG EXIF data can span multiple APP1 segments, so the size of one segment does not bound the total data passed to `Exif.load()`.

## libcurl

The MS Windows builds ship the OpenSSL variant of libcurl, without the curl command line tool or the GStreamer curl plugins.
Xpra uses it through libproxy to download proxy auto-configuration (PAC) files.
The [`libproxy 0.5.12` downloader](https://github.com/libproxy/libproxy/blob/0.5.12/src/backend/px-manager.c)
sets `CURLOPT_NOPROXY="*"`, bypassing proxies, and does not enable cookies, HSTS, Negotiate authentication,
client certificates, uploads, multipart MIME, FTP wildcard matching or interface binding.
It neither reads `.netrc` files nor queries `CURLINFO_EFFECTIVE_URL`.

It does enable `CURLOPT_FOLLOWLOCATION` without restricting redirect protocols.
Libcurl [allows HTTP, HTTPS, FTP and FTPS redirects by default](https://curl.se/libcurl/c/CURLOPT_REDIR_PROTOCOLS_STR.html),
so downloading a PAC file can reach the FTP control-response parser even when the configured PAC URL uses HTTP or HTTPS.
SCP, SFTP and TFTP redirects are rejected by default.

## XML data

Xpra does not use Python XML parsers on MS Windows.
Fontconfig uses Expat for local configuration files and
[creates and frees a parser for each document](https://gitlab.freedesktop.org/fontconfig/fontconfig/-/blob/2.18.3/src/fcxml.c), without `XML_ParserReset`.
The Expat parser in [D-Bus GLib 0.114](https://dbus.freedesktop.org/releases/dbus-glib/dbus-glib-0.114.tar.gz)
is part of its build tools, which are not bundled; its runtime introspection parser uses GLib's GMarkup.
The SVG loader uses libxml2 rather than Expat.

## Vulnerabilities

```shell
curl -sSfLO https://xpra.org/stable/windows/Xpra-x86_64_6.5.5-r0.json

GRYPE_MATCH_PYTHON_USING_CPES=true GRYPE_MATCH_RUST_USING_CPES=true grype sbom:sbom.json --by-cve -o json > grype.json
python3 packaging/MSWindows/sbom_vulnerabilities.py --scan 6.5.5-r0 grype.json --update
```
